# 用户结构：APK 观察与本站应用

## 结论

阅读工作台可以采用“发现 → 阅读 → 留存 → 回看与加工”的用户路径。把“我的”作为个人活动的稳定入口；公共文章保留一份，收藏、阅读状态、订阅与加工记录按用户归属。

这是一份产品结构建议。当前已核对静态 APK 和本站代码，尚未验收微信读书实际设备上的界面，也未实现本站的新用户体系。

## 推荐的用户页面结构

### 发现

全部动态是主入口，分类继续作为列表中的选项。热点、日报和主题为不同的探索方式，继续复用现有页面。

### 我的

从一个稳定入口查看收藏、最近阅读和加工记录。个人订阅放在此处，表达“我关注哪些来源”；后台信源管理继续承担采集配置与运维职责。阅读记录应支持回到上次阅读处，缺失位置时只显示已有的已读状态。

### 内容详情

保持原文、摘要和出处在阅读上下文中。收藏、继续阅读和交给阅读工具都是对当前内容的操作。加工记录要能回到原文和引用位置；存疑、失败、完成各有真实状态。

### 设置

集中组织外观、数据导入导出、同步状态和账号会话。当前只具备本机保存时继续明确告知。设置不占据内容发现的主位置。

首批优先级：先归整个人入口和空状态，再补有时间及位置的阅读记录；跨设备同步作为独立实现阶段，需要真实身份与隔离验收。社交关系、会员交易和公开个人主页没有当前需求依据，不列入首批。

## 推荐的数据职责

以下是目标职责划分，不是已创建的表，也不指定新的认证技术栈。

| 对象 | 职责 | 关键归属 |
| --- | --- | --- |
| 用户 | 稳定身份及展示资料 | 独立 `user_id`；邮箱、昵称均不能充当稳定主键 |
| 登录身份 | 外部登录方式与本地用户关联 | 登录渠道及其稳定主体映射到 `user_id` |
| 会话 | 某台设备或浏览器的授权及撤销 | 会话属于用户；多端分别登录 |
| 用户偏好 | 关注来源、默认筛选及阅读偏好 | 区分可同步偏好与当前设备外观 |
| 个人内容状态 | 收藏时间、最近阅读时间、阅读位置 | `(user_id, content_id)`；公共文章继续复用现有 ID |
| 个人加工记录 | 输入、引用、产出、状态及版本 | 用户归属与内容可见性；复用已有 workflow 和 `claims/documents/provenance` |
| 管理权限 | 管理采集、来源、模型及发布 | 明确的管理授权；普通登录不授予后台能力 |

本机收藏是当前有效数据。后续登录迁移应执行显式合并，保留原收藏时间，不能清空本机数据或覆盖云端记录。退出或切换用户后也不能展示上一用户的私有缓存。

LifeGame 后续可以共用这套身份和个人状态职责；其现有认证入口与数据模型本次未核对，不能声称已统一。

## 实施时的验收入口

- 未登录仍能阅读公开动态；个人状态准确标注为本机保存。
- 手机和电脑都能找到“我的”，旧 `/starred` 和内容链接保持可达。
- 明确区分本机保存、同步中、同步失败与已同步，失败不显示成功。
- 新用户导入已有收藏后核对数量、原时间和内容 ID；再重复导入验证无重复。
- 用两个用户验证个人记录隔离、退出及会话撤销；普通用户不能访问后台。
- 阅读位置与引用使用稳定内容 ID 和版本校验；正文变化时提示位置可能失效。
