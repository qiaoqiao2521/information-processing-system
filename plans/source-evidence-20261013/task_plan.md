# 引用定位与报告结构化

## 目标
修正来源路由与项目预算的冲突。复用来源包的 `claims/documents/provenance`，为引用生成编号、正文位置、原文位置与缺口报告。报告提取区分事实、作者建议、义务、例外与本文推演；责任人、期限没有证据时保留未知。

## 复用与边界
信息系统负责来源路由及交接契约；`xueyu-gongzhonghao/automation/daily-wechat` 负责可执行校验。结构化提取随既有 writer 调用返回，不新增模型轮次、数据库、定时器、通知或外部任务。普通网页不走 Jina；既有 X 正文只走现有预算入口。旧冻结运行不迁移、不重签。

## 步骤
1. 修订路由技能、参考表和遗留预处理器，验证失败保留来源。
2. 补确定性引用定位、正文 hash 和附件归档 hash 校验。
3. 补可选结构化提取并接入既有作者、复核与拒绝归档流程。
4. 验证误引、歧义、缺页码、未知责任人及期限等边界，提交推送两个仓库。
5. 按后续授权部署436，并以新的独立素材包做真实作者、独立复核和报告读回验收。

## 验收依据
采用 `Wiki/自动化开发范式与智能体协作.md` 的“按当前任务选择验收依据”和“内容质量与交付保真分开判断”。首轮验证离线行为与代码交付；后续生产验收分别核对436文件、真实模型回执、正文/附件hash、位置及分类。报告生成不等于微信投递验收。

## 实际结果

路由、预处理器和旧acquisition入口已修正。引用及结构化报告接入现有写作和独立复核；离线CLI可检查普通素材包与实际运行的隔离附件。公众号184项、信息系统27项测试通过，包含错误引用、hash、位置歧义、未知责任人/期限、报告篡改和旧预算绕路边界。代码交付与生产部署分别记录。

随后已部署436并补齐原生nullable类型兼容，本机202项公众号相关测试通过。真实报告经两次作者与两次独立复核完成引用对齐，5条claims的正文及原文位置均通过，8条结构化记录保留未知字段，最终hash与CLI重算一致。仍保留引用完备性缺口及非阻断编辑建议；详见progress.md。
